## Implementation boundary after selection

The current `src/server/v1/http.ts` catch logs only the error class and returns a sanitized 503; it does not notify an engineer. `src/server/v1/telemetry.ts` persists guest/staff errors and health checks but only makes them visible in Studio. Initial changes can stay outside `src/app/**`: server forwarding, committed-telemetry dispatch, a server-only alert module, supported framework instrumentation and tests. Read the installed Next.js instrumentation guide before implementing framework hooks. Announce any measured gap requiring an app-path edit before making it.

Use strict outgoing allowlists: environment, release, generated correlation ID, UTC occurrence time, category, approved check code and coarse browser family. Do not forward raw exception text, SQL, stacks, request bodies, headers, cookies, tokens, full URLs/query strings, guest names/businesses, email addresses or device/IP hashes. Public error responses remain unchanged. Exclude expected BELOW_MINIMUM, ALREADY_LEADING and CLOSED decisions and ordinary device reports.

Dispatch only after durable application transactions complete, using bounded background work supported by the runtime. Never put provider I/O inside the bid lock/transaction. Bound deduplication entries and TTL; process-local deduplication alone must not be described as global under Fluid scaling. Provider per-issue throttling provides an additional repetition limit. Bound timeout/retries and maintain safe local failure records. A failed notification must not turn a committed bid or telemetry report into an unconfirmed/failed application response, and must not recursively alert.

Local tests must prove outgoing filtering, first delivery, repeated-event suppression, bounded eviction/expiry, transport timeout/failure behavior, disarmed configuration, no client credential inclusion and unchanged durable bid/receipt behavior. A stub receiver demonstrates the local send contract only, not Sentry detection or engineer receipt.
